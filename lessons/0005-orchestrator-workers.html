Orchestrator-workers: i sotto-task li decide il modello, non tu

Lezione 0005 — il quarto pattern, il primo dove la struttura stessa non è fissata in anticipo

Nella lezione 0004 l'ultima domanda del quiz ha già messo il dito sul punto: in parallelization tu decidi, nel codice, quali sotto-task lanciare — tre chiamate fisse per sicurezza, performance, stile. In orchestrator-workers quella lista non esiste ancora quando scrivi il codice: un LLM centrale (l'orchestrator) legge il task specifico e decide lui, a runtime, in quanti sotto-task scomporlo e cosa delegare a ciascuno1.

1. Building effective agents — Anthropic Engineering, sezione "Orchestrator-workers": "the orchestrator LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results" — e la differenza esplicita da parallelization: "subtasks aren't pre-defined, but determined by the orchestrator based on the specific input".

Cosa resta fisso, e cosa no

Attenzione a non scivolare verso "allora è un agent, non un workflow": il ciclo orchestratore→delega→sintesi resta un predefined code path, esattamente come negli altri quattro pattern — lo scrivi tu, gira sempre uguale. Quello che cambia è solo il contenuto di quel ciclo: il numero di worker e il loro compito sono l'output di una chiamata LLM (l'orchestrator), non una costante che hai scritto tu. È la stessa distinzione workflow/agent della lezione 0001, applicata dentro un singolo step invece che all'intero sistema.

Quanti worker (2? 5?) e cosa fa ciascuno non è scritto nel codice: lo decide l'orchestrator leggendo il task specifico. Solo il ciclo pianifica→delega→sintetizza è fisso — è questo, non il numero di worker, a renderlo ancora un workflow.

Quando usarlo

Orchestrator-workers conviene quando non puoi prevedere in anticipo la scomposizione del task — es. "rifattorizza questa funzione ovunque venga usata nel codebase": non sai quanti file la usano finché non guardi2. Se invece i sotto-task sono sempre gli stessi (sempre "sicurezza, performance, stile"), non ti serve un orchestrator: torna a parallelization, che è più semplice da debuggare perché la struttura è visibile leggendo il codice, non nascosta nell'output di una chiamata LLM.

2. Esempio di Anthropic: coding task dove "the exact set of files that need to change" dipende dalla natura specifica di ogni richiesta.

Alla fine di questa lezione saprai: distinguere orchestrator-workers da parallelization sulla base di UNA domanda ("il numero di sotto-task è fisso nel codice o deciso a runtime?"), riconoscere Subagent come primitiva concreta dietro ogni worker, e scrivere un orchestrator con agent() + parallel() nel Workflow tool.

Mapping su Claude Code e sul Workflow tool

Questo pattern non è astratto per te: lo stai osservando dal vivo in questa sessione. Quando in questa conversazione delego una ricerca ampia a un subagent tramite l'Agent tool, io (l'orchestrator) decido a runtime se e quanti subagent lanciare, e con che istruzioni — non è pre-scritto quale subagent userò finché non leggo la tua richiesta. Il Subagent (già nel glossario dalla lezione 0001) è la primitiva concreta dietro ogni worker.

Nel Workflow tool, lo stesso pattern si scrive componendo i due primitivi che già conosci: un agent() iniziale che produce un piano (numero e contenuto dei sotto-task), seguito da un parallel() che esegue esattamente quel piano — non uno fissato da te in anticipo. 

const plan = await agent(
  `Scomponi questo refactoring in sotto-task indipendenti, uno per file da modificare: ${task}`,
  { schema: PLAN_SCHEMA }   // { subtasks: [{ file, istruzioni }, ...] } — la lunghezza non è nota in anticipo
)

const results = await parallel(
  plan.subtasks.map(st => () => agent(st.istruzioni, { schema: RESULT_SCHEMA }))
)

const synthesis = await agent(
  `Sintetizza questi risultati in un unico riepilogo: ${JSON.stringify(results)}`
)

Confronta con il codice della lezione 0004: lì parallel() riceveva un array di thunk scritto a mano, di lunghezza 3, fissa. Qui riceve plan.subtasks.map(...) — un array la cui lunghezza è decisa dall'orchestrator, chiamata dopo chiamata. parallel() è lo stesso primitivo; cambia solo da dove viene l'input.
