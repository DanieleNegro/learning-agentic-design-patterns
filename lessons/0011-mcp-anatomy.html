Anatomia di MCP: aggiungere capacità, non istruzioni

Lezione 0011 — ultimo asse scoperto della mission

Hai chiuso due assi con artefatti reali: una Skill (0008) e un Hook (0010). Entrambi agiscono su ciò che Claude Code già sa fare: la Skill inietta istruzioni nel context, l'Hook esegue codice tuo a un punto fisso del ciclo di vita. Nessuno dei due gli dà un tool che non aveva.

MCP (Model Context Protocol) è il terzo tipo di estensione, ed è l'unico che allarga la superficie di tool dell'harness: un processo separato espone tool, dati e prompt tramite un protocollo aperto, e Claude Code li monta come se fossero suoi1.

1. MCP — Claude Code Docs: "MCP is an open-source standard for AI-tool integrations… MCP servers give Claude Code access to your tools, databases, and APIs."

Tre estensioni, tre cose diverse

Il perno di questa lezione è la distinzione, non la sintassi. Context, controllo e capacità sono tre problemi separati, e ogni meccanismo ne risolve uno solo.

Skill e Hook vivono dentro l'harness e lavorano su capacità già esistenti. L'MCP server è fuori dal processo: parla un protocollo, e in cambio l'harness guadagna tool che prima non aveva — esposti con un nome namespaced.

Tre assi: transport, scope, surface

Come l'Hook si leggeva in tre livelli (evento → matcher → handler), una configurazione MCP si legge su tre assi indipendenti2.

2. MCP — Claude Code Docs, sezioni "Transport types", "MCP installation scopes" e "MCP tool naming".

AsseCosa decideValori
Transport Come Claude Code parla col server stdio (processo locale), http (remoto, raccomandato), sse (deprecato), ws (solo via JSON)
Scope Chi vede il server, e se è condiviso local (default, privato, questo progetto), project (.mcp.json, versionato), user (tutti i tuoi progetti)
Surface Cosa il server espone tools (mcp__server__tool), resources (@mention), prompts (/slash)

I due comandi che coprono il 90% dei casi — un server locale e uno remoto. Tutto ciò che sta dopo -- viene passato al server senza essere interpretato3:

3. Dimenticare il -- è l'errore classico: Claude Code prova a parsare i flag del server come suoi. Nell'ambiente dello stdio server viene iniettata CLAUDE_PROJECT_DIR — la stessa variabile che è servita a riparare il tuo hook nella 0010.

# stdio: un processo locale, con env var
claude mcp add --transport stdio db --env PGPASSWORD=segreto \
  -- npx -y @bytebase/dbhub --dsn "postgresql://readonly@localhost/analytics"

# http: un server remoto, condiviso col team via .mcp.json
claude mcp add --transport http --scope project notion https://mcp.notion.com/mcp

claude mcp list     # stato di salute di ogni server
/mcp                # pannello dentro la sessione: auth, enable/disable

Lo scope project è quello che si committa, e per questo ha una regola di sicurezza sua: un server dichiarato in .mcp.json richiede la tua approvazione esplicita in sessione interattiva — ma in claude -p, nell'Agent SDK e nelle sessioni cloud viene caricato senza chiedere4. Un .mcp.json che arriva da una pull request è codice eseguibile che entra nel tuo harness.

4. MCP — Claude Code Docs, "Project scope → Approvals". Reset delle scelte con claude mcp reset-project-choices.

Il criterio di scelta: quando MCP non conviene

L'obiettivo di mission non è "collegare un server", è sapere quando MCP è la scelta giusta rispetto a una Skill o a un tool custom. La documentazione dà un'euristica sobria: collega un server quando ti accorgi di copiare dati a mano nella chat da un altro sistema5.

5. MCP — Claude Code Docs: "Connect a server when you find yourself copying data into chat from another tool."

Il rovescio conta di più, perché è quello che si sbaglia. MCP ha un costo che una Skill non ha: le definizioni dei tool occupano context window, e l'output di un tool ha un tetto — warning a 10.000 token, massimo di default 25.000, oltre il quale il risultato viene scritto su file e sostituito dal path6. Quindi:

6. MCP — Claude Code Docs, "MCP output limits". Il tetto si alza con MAX_MCP_OUTPUT_TOKENS.

  • Esiste già una CLI (gh, psql, kubectl)? Una Skill che insegna a Claude come usarla via Bash costa quasi nulla e non aggiunge un processo. Riesporre quella CLI dietro un MCP server è lavoro in più per lo stesso risultato.
  • Il sistema è remoto, API-only, o con auth complicata (OAuth, token a vita breve)? Qui MCP guadagna il suo posto: gestisce il flusso di login, il refresh dei token e li tiene fuori dal tuo codice.
  • Serve in più client (Claude Code, Claude Desktop, Cursor)? Questa è la ragione forte, e non è la potenza: è che il protocollo è aperto. Un server si scrive una volta e vale per tutti; una Skill vale solo dentro Claude Code.

Ultimo dettaglio operativo che tornerà utile: i tool MCP arrivano al modello con nome mcp__<server>__<tool>. È quel nome completo — non quello interno del server — che va scritto nelle permission rule, negli allowed-tools di una Skill, nel campo tools di un subagent e nei matcher degli Hook7. Il tuo hook della 0010 sorveglia il matcher Bash: un tool MCP non passa da lì.

7. MCP — Claude Code Docs, "MCP tool naming and namespacing". Ogni carattere fuori da A-Z a-z 0-9 _ - diventa _.

Alla fine di questa lezione saprai: dire in una frase cosa aggiunge MCP che Skill e Hook non possono aggiungere, leggere una configurazione sui tre assi transport / scope / surface, riconoscere il caso in cui una Skill batte un MCP server, e sapere con quale nome un tool MCP va citato in una permission rule o in un matcher.
