Evaluator-optimizer: il primo pattern con un ciclo

Lezione 0006 — il quinto e ultimo pattern nominato da Anthropic, e chiude l'arco iniziato nella lezione 0001

Tutti e quattro i pattern visti finora — chaining, routing, parallelization, orchestrator-workers — sono grafi aciclici: l'esecuzione va sempre avanti, mai indietro. Evaluator-optimizer è il primo che introduce un ciclo esplicito: un LLM genera una risposta, un secondo LLM la valuta rispetto a criteri e restituisce feedback, e se la risposta non soddisfa i criteri viene rigenerata con quel feedback — da capo, finché l'evaluator non approva1.

1. Building effective agents — Anthropic Engineering, sezione "Evaluator-optimizer": "one LLM call generates a response while another provides evaluation and feedback in a loop".

Il confronto che conta: gate vs evaluator

Nella lezione 0002 il gate, se falliva, fermava il workflow — un'unica direzione, avanti o stop. Qui, se l'evaluator boccia la risposta, il flusso non si ferma: torna indietro allo step di generazione, portando con sé un feedback specifico su cosa correggere. È questo loop — non la semplice presenza di due chiamate LLM in sequenza — a distinguere evaluator-optimizer da prompt chaining con un gate.

Anthropic identifica due segnali che indicano che vale la pena usare questo pattern2: primo, un umano che esprime un feedback esplicito migliora dimostrabilmente la risposta; secondo, l'LLM stesso è in grado di produrre un feedback di quella qualità. Se manca il secondo segnale — l'LLM non sa giudicare bene le proprie uscite secondo quei criteri — il ciclo rigenera senza convergere, e il pattern non paga il costo aggiuntivo.

2. Testuale: "the LLM response can be demonstrably improved when a human articulates their feedback" e "the LLM can provide such feedback" — per analogia, il processo di scrittura iterativo di uno scrittore umano.

A differenza del gate (lezione 0002), un rifiuto qui non ferma il workflow: torna a Generate con un feedback specifico, e il ciclo si ripete finché Evaluate non approva.

Alla fine di questa lezione saprai: distinguere evaluator-optimizer da prompt chaining sulla base della direzione del flusso (avanti-e-stop vs ciclo-con-feedback), riconoscere i due segnali che indicano se vale la pena usarlo, e scriverlo come un while loop nel Workflow tool — chiudendo la copertura di tutti e cinque i pattern di "Building effective agents".

Mapping sul Workflow tool di Claude Code

Non serve un primitivo nuovo: evaluator-optimizer è un while ordinario attorno a due agent() — uno che genera, uno che valuta — esattamente lo schema "loop-until" che il Workflow tool usa per accumulare risultati fino a un target. Qui il "target" è "l'evaluator approva", non un conteggio. 

let draft = await agent(
  `Scrivi una bozza di changelog da questi commit: ${commits}`,
  { schema: DRAFT_SCHEMA }
)

let evaluation = await agent(
  `Valuta questa bozza secondo lo stile del progetto, elenca cosa manca: ${draft.testo}`,
  { schema: EVAL_SCHEMA }   // { approvato: bool, feedback: string }
)

while (!evaluation.approvato) {
  draft = await agent(
    `Rigenera la bozza applicando questo feedback: ${evaluation.feedback}\n\nBozza precedente: ${draft.testo}`,
    { schema: DRAFT_SCHEMA }
  )
  evaluation = await agent(`Valuta di nuovo: ${draft.testo}`, { schema: EVAL_SCHEMA })
}

Confronta con il gate della lezione 0002: lì un if semplice decideva se proseguire. Qui il controllo è un while, perché il flusso può tornare allo stesso step generate un numero di volte non noto in anticipo — proprio come non sapevi in anticipo il numero di worker nell'orchestrator-workers, qui non sai in anticipo quanti cicli servono per convergere.
