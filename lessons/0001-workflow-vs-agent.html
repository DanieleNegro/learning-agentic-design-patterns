Workflow vs Agent: la distinzione fondamentale

Lezione 0001 — e dove si inseriscono Skill, Hook, MCP e Subagent di Claude Code

Prima di costruire qualunque workflow agentico per lo sviluppo software con Claude Code, serve un asse di riferimento: quando stai costruendo un workflow e quando stai costruendo un agent? Anthropic li definisce in modo preciso nel suo articolo di riferimento1, e questa distinzione è il primo criterio di design che userai ogni volta che devi scegliere tra una Skill, un Hook, un server MCP o un Subagent.

1. Building effective agents — Anthropic Engineering. Fonte primaria di tutta questa lezione.

Il building block di base: Augmented LLM

Ogni pattern agentico, workflow o agent che sia, è costruito sopra lo stesso mattone: un Augmented LLM — un LLM potenziato con retrieval, tools e memory, che il modello stesso sceglie attivamente di usare in base al contesto2. In Claude Code, questo potenziamento arriva soprattutto tramite MCP (Model Context Protocol) e i tool built-in (Read, Bash, WebFetch, ...).

2. Il modello decide se e come usare uno strumento — non è un'invocazione hardcoded. Questa è la differenza tra "tool disponibile" e "tool use" effettivo.

La distinzione: Workflow vs Agent

WorkflowAgent
Definizione LLM e tool orchestrati attraverso predefined code paths — il flusso di controllo lo scrivi tu. L'LLM dirige dinamicamente il proprio processo e l'uso dei tool — il flusso di controllo lo decide il modello, passo dopo passo, in un loop.
Quando usarlo Il task si scompone in sotto-task noti e fissi in anticipo. Preferisci prevedibilità e latenza controllata. Il task è open-ended, il numero di step non è prevedibile, e ti puoi fidare del giudizio del modello passo-passo.
Costo del fallimento Contenuto — ogni step è verificabile e ha un "gate" programmatico. Più alto — richiede tool ben documentati (Agent-Computer Interface) e spesso checkpoint umani.

Alla fine di questa lezione saprai: dato un meccanismo di Claude Code (Skill, Hook, MCP, Subagent), dire subito se appartiene al lato "workflow" o al lato "agent" dell'asse — e quindi scegliere il primitivo giusto quando progetti un workflow di sviluppo.

Cinque pattern di workflow, in una riga ciascuno

Anthropic ne nomina cinque, tutti a "predefined code path" — li approfondiremo uno per uno nelle prossime lezioni. Per ora, solo i nomi e l'idea:

  • Prompt chaining: step sequenziali, ognuno valida l'output del precedente.
  • Routing: classifica l'input e lo instrada verso un handler specializzato.
  • Parallelization: sectioning (sotto-task indipendenti) o voting (più tentativi sullo stesso task).
  • Orchestrator-workers: un LLM centrale scompone il task dinamicamente e delega a worker.
  • Evaluator-optimizer: un LLM genera, un altro valuta e dà feedback, in loop.

3. Nota che "orchestrator-workers" ha una scomposizione dinamica dei sotto-task — è il pattern più vicino al confine con "agent", pur restando un workflow perché il ciclo orchestratore→worker→sintesi è comunque codice fisso.

Mapping sui building block di Claude Code

PrimitivoCosa faDove si colloca sull'asse
Skill File SKILL.md con istruzioni/conoscenza, caricato on-demand tramite progressive disclosure4 quando la descrizione matcha il task. Trasversale: è conoscenza modulare per l'Augmented LLM, non un controllo di flusso — utilizzabile sia dentro un workflow che dentro un agent.
Hook Comando shell/HTTP/MCP eseguito automaticamente a un evento fisso del ciclo di vita (PreToolUse, PostToolUse, SessionStart, ...)5, con potere di allow/deny/modify. Puro lato workflow: è letteralmente un "predefined code path" che gira indipendentemente da cosa decide il modello.
MCP Protocollo standard per collegare l'LLM a sistemi esterni: database, API, browser6. È il canale con cui l'Augmented LLM ottiene retrieval/tools/memory — il building block di base, non un pattern di per sé.
Subagent Agente delegato con proprio contesto separato, invocato dal main agent tramite il tool Agent7. La primitiva concreta dietro orchestrator-workers: il main agent decide dinamicamente cosa delegare.

Mettiti alla prova

1. Un sistema di triage ticket: prima classifica sempre la categoria (bug, domanda, richiesta feature), poi chiama sempre lo stesso prompt specializzato per quella categoria. Che cos'è?

2. Un sistema a cui dai "fai passare la test suite" e che, non sapendo in anticipo quanti file dovrà toccare né in che ordine, decide da solo cosa leggere, modificare e ritestare finché i test sono verdi. Che cos'è?

3. Vuoi garantire che OGNI Edit su un file venga sempre seguito da un linter, indipendentemente da cosa "pensa" il modello. Quale primitivo di Claude Code usi?

4. Devi far interrogare a Claude Code, dal vivo, un database Postgres di produzione durante la sessione. Quale primitivo usi per collegarlo?

5. "Refactora questo modulo ovunque serva nel repo": il numero e la natura delle sotto-modifiche non sono noti in anticipo, e vuoi che ogni sotto-modifica lavori nel proprio contesto isolato. Quale primitivo useresti?
