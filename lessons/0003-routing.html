Routing: un solo branch, scelto a runtime

Lezione 0003 — il secondo pattern, e perché nel Workflow tool non serve un primitivo dedicato

Nella lezione 0002 hai visto prompt chaining: più step, tutti eseguiti in sequenza, sullo stesso input che si trasforma passo dopo passo. Routing è diverso: classifica l'input e lo instrada verso un solo handler specializzato, scelto tra più possibili — gli altri handler semplicemente non vengono eseguiti1. Lo avevi già incontrato di sfuggita nel quiz 0001 e nell'ultima domanda del quiz 0002: qui lo tratti come pattern a sé.

1. Building effective agents — Anthropic Engineering, sezione "Routing".

Definizione e il perché della separazione

Il punto di routing non è solo "smistare traffico": è separation of concerns. Invece di scrivere un unico prompt che deve gestire bene ogni possibile categoria di input — bug report, feature request, domanda generica — scrivi un handler per categoria, ognuno ottimizzato solo per il proprio caso2. Il classifier che decide quale handler chiamare può essere un'altra chiamata LLM, oppure un classificatore tradizionale — l'importante è che la scelta del branch resti codice fisso, non una decisione presa step-by-step dal modello dentro un loop.

2. Anthropic lo descrive come: "routing works well for complex tasks where there are distinct categories that are better handled separately, and where classification can be handled accurately, either by an LLM or a more traditional classification model/algorithm."

Il classifier è una singola chiamata LLM; quale branch si accende (qui, Handler B) dipende dal suo output — ma la struttura dei branch e la decisione di seguirne uno solo restano scritte da te, in anticipo.

Quando usarlo

Routing conviene quando riconosci categorie distinte nel tuo input, e ognuna beneficia di un prompt (o anche di un modello) diverso — per esempio domande semplici instradate a un modello economico e veloce, domande complesse a un modello più capace3. Non conviene se le categorie si sovrappongono molto, o se il classifier stesso è inaffidabile: un routing sbagliato manda l'input all'handler sbagliato senza possibilità di recupero, a meno che tu non aggiunga un fallback esplicito.

3. Esempio citato da Anthropic: instradare domande facili a Claude Haiku e domande difficili/insolite a un modello più capace, per bilanciare costo e qualità.

Alla fine di questa lezione saprai: riconoscere uno scenario di routing e distinguerlo da prompt chaining e da parallelization, spiegare perché la separazione in handler specializzati migliora l'accuratezza, e scrivere un routing nel Workflow tool senza cercare un primitivo che non esiste.

Mapping sul Workflow tool di Claude Code

A differenza di prompt chaining e parallelization, il Workflow tool non ha un primitivo dedicato per routing — e questo è il punto da ricordare, non una lacuna. Routing è già codice fisso ordinario: un agent() di classificazione, seguito da un if/switch JavaScript qualunque che decide quale agent() chiamare dopo. Non c'è bisogno di pipeline() (che farebbe passare tutti gli item per tutti gli stage) né di parallel() (che eseguirebbe più branch contemporaneamente, aspettandoli tutti): routing esegue esattamente un branch, deciso dal risultato della classificazione. 

const classification = await agent(
  `Classifica questa richiesta in bug, feature o domanda generica: ${input}`,
  { schema: CLASS_SCHEMA }
)

const result =
  classification.categoria === "bug"
    ? await agent(`Gestisci come bug report: ${input}`, { schema: BUG_SCHEMA })
    : classification.categoria === "feature"
    ? await agent(`Gestisci come feature request: ${input}`, { schema: FEATURE_SCHEMA })
    : await agent(`Rispondi alla domanda generale: ${input}`)

Nota cosa succede se hai una lista di richieste da instradare: usi comunque pipeline() per farle scorrere una alla volta attraverso "classifica poi instrada", ma il secondo stage della pipeline è questo blocco condizionale — routing e prompt chaining non si escludono, si compongono.

Mettiti alla prova

1. Un ticket di supporto viene prima classificato come "billing", "technical" o "general", poi inviato a UN SOLO prompt specializzato per quella categoria. Che pattern è?

2. Come si chiama, nel vocabolario del pattern, lo step che decide quale handler riceverà l'input?

3. Quale primitivo del Workflow tool implementa direttamente il routing, così come pipeline() implementa prompt chaining?

4. Perché scrivere tre handler distinti per bug/feature/domanda invece di un unico prompt generico che gestisce tutti i casi?

5. Se invece la stessa richiesta venisse fatta passare per PIÙ handler contemporaneamente, e i risultati aggregati insieme, che pattern sarebbe?
