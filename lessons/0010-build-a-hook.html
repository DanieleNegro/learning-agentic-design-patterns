Costruisci il tuo primo Hook: blocca il force-push

Lezione 0010 — lezione pratica, come la 0008 per le skill: qui costruisci l'artefatto, non solo la teoria

La lezione 0009 ti ha dato evento → matcher → handler e la semantica degli exit code. Questa lezione ti fa scrivere un Hook vero, che gira davvero: blocca git push --force su qualunque repository in cui lavori, prima ancora che Claude Code ti chieda il permesso. È l'obiettivo dichiarato nella tua mission: "ha configurato almeno un Hook... per automatizzare un comportamento del proprio harness".

Perché questo esempio, non un altro

Non è un esempio inventato: il "Git Safety Protocol" di questa stessa sessione dice esplicitamente di non fare mai force-push senza una richiesta esplicita — ma è una regola scritta, che il modello segue perché gliel'ho chiesto, non perché sia strutturalmente impossibile violarla1. Qui trasformi quella regola in qualcosa che gira sempre, a prescindere da cosa "decide" il modello in quel momento — esattamente la distinzione centrale della 0009.

1. Non stai duplicando una protezione già perfetta: stai aggiungendo un livello che non dipende da come il modello interpreta le istruzioni in un dato momento.

Due cose nuove prima di scrivere

Dove vive la configurazione. ~/.claude/settings.json è personale — si applica a tutti i tuoi progetti, non solo a questo. Un hook di sicurezza su git push è per definizione qualcosa che vuoi ovunque, non solo qui: stessa logica già vista per le skill personali in 00082.

2. Hooks reference — Claude Code Docs, tabella "Hook Locations and Scope".

Leggere tool_input.command. Il tuo script riceve JSON su stdin; jq -r '.tool_input.command' estrae la stringa del comando Bash che Claude sta per eseguire, così puoi ispezionarla prima che parta.

Alla fine di questa lezione avrai: un hook personale funzionante che blocca ogni git push --force in qualunque tuo progetto, e saprai spiegare perché vive in ~/.claude/settings.json e non in un file di progetto.

Passo 1 — lo script

Crea la cartella e lo script che ispeziona il comando:

mkdir -p ~/.claude/hooks
# ~/.claude/hooks/block-force-push.sh
#!/bin/bash
COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -qE 'git push .*(--force|-f)\b'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Force push bloccato da hook personale: rimuovi --force o chiedi conferma esplicita."
    }
  }'
else
  exit 0
fi
chmod +x ~/.claude/hooks/block-force-push.sh

Passo 2 — registra l'hook

Aggiungi in ~/.claude/settings.json (crealo se non esiste):

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/block-force-push.sh"
          }
        ]
      }
    ]
  }
}

Nota il matcher: "Bash": come nell'esempio della 0009, restringe l'hook ai soli tool call Bash — non gira per Read, Edit o altri tool dove tool_input.command non esisterebbe nemmeno.

Passo 3 — testalo davvero

Apri una nuova sessione di Claude Code (le modifiche a settings.json si caricano all'avvio) e chiedile di eseguire git push --force in un repository di prova — o anche solo echo "git push --force origin main" passato a un comando Bash reale per vedere il blocco scattare. Il feedback loop è immediato: o il permesso viene negato con la tua permissionDecisionReason, o l'hook ha un errore di sintassi da correggere3.

3. Per debuggare uno script che non si comporta come previsto, testalo isolato da riga di comando: echo '{"tool_input":{"command":"git push --force origin main"}}' | ~/.claude/hooks/block-force-push.sh — deve stampare il JSON di deny.

Mettiti alla prova

1. Perché questo hook va in ~/.claude/settings.json invece che in .claude/settings.json di un singolo progetto?

2. Lanci "git push origin main" (senza --force). Cosa fa lo script?

3. Come fa lo script a sapere qual è il comando che Claude sta per eseguire?

4. Quando il grep trova un match, lo script stampa JSON con permissionDecision: "deny" ed esce con 0, non con 2. Perché funziona comunque?

5. Se Claude prova a leggere un file (tool Read) invece di lanciare Bash, questo hook interviene?
