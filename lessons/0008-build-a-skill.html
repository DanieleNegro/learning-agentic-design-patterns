Costruisci la tua prima Skill: checklist di code review

Lezione 0008 — lezione pratica, non un altro quiz: qui costruisci l'artefatto che la mission chiede

La lezione 0007 ti ha dato l'anatomia. Questa lezione ti fa scrivere una Skill vera, che userai davvero: una checklist di code review con i tuoi criteri, invocabile con /review-checklist su qualunque diff, in qualunque tuo progetto. È esattamente l'obiettivo dichiarato nella tua mission: "ha costruito almeno una Skill custom... che incapsula un workflow di sviluppo ricorrente".

Due concetti nuovi che ti servono prima di scrivere il file

Dynamic context injection. Una riga come !`git diff HEAD` dentro SKILL.md non dice a Claude "esegui questo comando quando vuoi": il comando gira prima, come preprocessing, e il suo output sostituisce il placeholder — Claude riceve il diff già incollato nel testo, non un invito a lanciare git da solo1.

1. Extend Claude with skills — Claude Code Docs, sezione "Inject dynamic context": "This is preprocessing, not something Claude executes. Claude only sees the final result."

$ARGUMENTS. Se lanci /review-checklist src/api.ts, tutto ciò che scrivi dopo il nome della skill sostituisce letteralmente $ARGUMENTS ovunque compaia nel corpo — così la stessa skill può rivedere "il diff corrente" di default, o un file specifico se lo indichi2.

2. Se non usi $ARGUMENTS nel testo, Claude Code lo appende comunque in coda come ARGUMENTS: <input> — non sparisce mai silenziosamente.

Alla fine di questa lezione avrai: una Skill personale funzionante in ~/.claude/skills/review-checklist/, capirai perché sta a livello personale e non di progetto, e saprai spiegare cosa fanno dynamic context injection e $ARGUMENTS in quel file specifico.

Passo 1 — dove metterla

Una checklist di code review è un criterio tuo, che vuoi applicare in ogni repository su cui lavori — non solo in questo. Per questo va in una skill personale, non di progetto3: 

mkdir -p ~/.claude/skills/review-checklist

3. Dalla tabella "Where skills live": ~/.claude/skills/<skill-name>/SKILL.md → "Applies to: All your projects", contro .claude/skills/ → "This project only".

Passo 2 — scrivi SKILL.md

Questo è uno scheletro da completare con i tuoi criteri reali — i quattro punti sotto sono segnaposto generici, non la tua checklist. Sostituiscili prima di salvare. 

---
name: review-checklist
description: Applica la mia checklist di code review al diff corrente o a un file specifico. Usa quando chiedo di rivedere del codice secondo i miei criteri standard.
disable-model-invocation: true
argument-hint: "[percorso file, opzionale]"
---

## Codice da rivedere

$ARGUMENTS

!`git diff HEAD`

## Checklist

Per ognuno di questi punti, valuta il codice sopra e segnala esplicitamente pass/fail con la riga interessata.
Non aggiungere osservazioni fuori da questi punti, a meno che non sia un bug palese.

1. [SOSTITUISCI: es. "Ogni funzione pubblica ha un test"]
2. [SOSTITUISCI: es. "Nessun valore hardcoded che dovrebbe essere config"]
3. [SOSTITUISCI: es. "Gli errori esterni (rete, I/O) sono gestiti, non ignorati"]
4. [SOSTITUISCI: il tuo criterio più ricorrente — quello che finisci sempre per far notare a voce]

Nota disable-model-invocation: true: lo stesso campo della lezione 0007, qui applicato a una scelta tua. Vuoi decidere tu quando far partire una review, non che Claude la lanci di propria iniziativa perché la conversazione "sembra" in tema di codice.

Passo 3 — testala

Vai in un progetto con modifiche non committate e lancia /review-checklist. Poi prova anche /review-checklist src/qualcosa.ts per vedere $ARGUMENTS in azione. Il feedback loop qui è il più stretto possibile: o la skill applica davvero i tuoi criteri, o non lo fa — e lo vedi subito, non devi indovinare4.

4. Se Claude non la invoca o la applica male, la documentazione raccomanda di confrontare una sessione con la skill e una senza, prima di riscrivere la description — vedi "Evaluate and iterate on a skill" nella fonte citata sotto.

Mettiti alla prova

1. La riga !`git diff HEAD` dentro SKILL.md: quando viene eseguita, esattamente?

2. Vuoi che Claude proponga questa skill da solo quando gli scrivi "rivedimi questo codice", senza che tu debba digitare /review-checklist. Quale campo del frontmatter è decisivo per questo?

3. Lanci /review-checklist src/api.ts. Cosa succede a $ARGUMENTS nel corpo della skill?

4. Perché disable-model-invocation: true ha senso per una skill di code review personale, e non solo per un /deploy?

5. Perché questa skill va in ~/.claude/skills/ (personale) invece che in .claude/skills/ di un singolo progetto?
