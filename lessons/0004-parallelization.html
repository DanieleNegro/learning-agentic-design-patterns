Parallelization: nessuna dipendenza, aggregazione fissa

Lezione 0004 — il terzo pattern, e la barriera esplicita di parallel()

Nella lezione 0003 un solo branch veniva eseguito, scelto da un classifier. Parallelization è l'opposto: più chiamate LLM partono nello stesso momento, senza che una dipenda dall'output dell'altra, e i risultati vengono aggregati programmaticamente alla fine1. Nessun classifier decide "quale": partono tutte, sempre.

1. Building effective agents — Anthropic Engineering, sezione "Parallelization".

Due varianti, stessa struttura

Anthropic distingue due varianti2. Sectioning: scomponi un task in sotto-task indipendenti e distinti — es. controlla lo stesso pezzo di codice per bug di sicurezza, di performance e di stile, in tre chiamate parallele, poi unisci i tre report in uno solo. Voting: fai eseguire lo stesso identico task più volte in parallelo, e prendi il risultato di maggioranza o il consenso — utile quando vuoi più "opinioni" indipendenti sulla stessa domanda per alzare la confidenza (es. più chiamate che valutano indipendentemente se un contenuto viola una policy).

2. Testuale: "Sectioning: Breaking a task into independent subtasks run in parallel. Voting: Running the same task multiple times to get diverse outputs."

Le tre chiamate partono nello stesso momento, senza dipendenza tra loro — a differenza del routing, qui non c'è un nodo decisionale che ne sceglie una sola. L'aggregazione che le riunisce è codice fisso, scritto da te.

Quando usarlo

Sectioning conviene quando il task si scompone in aspetti davvero indipendenti — nessuno ha bisogno dell'output degli altri per essere svolto — e parallelizzarli riduce la latenza totale rispetto a farli in sequenza. Voting conviene quando un singolo tentativo è rumoroso e più tentativi indipendenti, aggregati per maggioranza, danno un risultato più affidabile di uno solo3.

3. Il costo è ovvio: N chiamate invece di una, eseguite in parallelo per contenere la latenza ma non il costo in token/richieste.

Alla fine di questa lezione saprai: distinguere parallelization da routing (nessun branch scelto, li eseguono tutti) e da prompt chaining (nessuna dipendenza sequenziale tra le chiamate), riconoscere sectioning vs voting, e scrivere una parallelizzazione con parallel() nel Workflow tool.

Mapping sul Workflow tool di Claude Code

parallel() implementa parallelization letteralmente: è una barriera — lancia tutti i thunk insieme e aspetta che finiscano tutti prima di restituire l'array dei risultati. L'aggregazione (il nodo "Aggregate" nel diagramma) è il codice ordinario che scrivi dopo l'await, non un'altra chiamata decisionale del modello. 

const [sicurezza, performance, stile] = await parallel([
  () => agent(`Controlla vulnerabilità di sicurezza in questo diff: ${diff}`, { schema: REVIEW_SCHEMA }),
  () => agent(`Controlla problemi di performance in questo diff: ${diff}`, { schema: REVIEW_SCHEMA }),
  () => agent(`Controlla violazioni di stile in questo diff: ${diff}`, { schema: REVIEW_SCHEMA }),
])

const report = [sicurezza, performance, stile]   // <- aggregazione: codice fisso, non un'altra agent()
  .filter(Boolean)
  .flatMap(r => r.findings)

Nota il contrasto con pipeline(): lì lo stage n dipende dall'output dello stage n-1, quindi un item può avanzare più velocemente di un altro (nessuna barriera). Qui invece parallel() è la barriera — tutti i thunk devono finire prima che tu possa procedere con l'aggregazione.
