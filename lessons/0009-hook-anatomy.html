Anatomia di un Hook: applicare, non chiedere

Lezione 0009 — terzo asse della mission, in contrasto diretto con quello appena chiuso

Hai appena chiuso l'asse Skill: un file che Claude legge e segue, per sua scelta o su tuo comando esplicito. Un Hook è l'opposto strutturale: un comando shell che gira sempre a un punto fisso del ciclo di vita, indipendentemente da cosa il modello "decide"1. Il glossario lo definiva già così dalla lezione 0001 — qui vedi perché quella distinzione conta davvero.

1. Hooks reference — Claude Code Docs: "The model can be asked to follow rules, but hooks enforce them."

Il problema che una Skill non può risolvere

Potresti scrivere in CLAUDE.md o in una Skill: "non lanciare mai rm -rf". Claude di solito obbedisce. Ma "di solito" non è una garanzia — è una richiesta che il modello potrebbe violare in certe condizioni. Un Hook risolve un problema diverso: non "convincere" Claude a non farlo, ma impedirlo strutturalmente, con codice che gira prima che il tool venga eseguito e può bloccarlo2.

2. Stesso principio di disable-model-invocation visto per le Skill (0007, 0008), ma spinto un livello più in basso: lì decidevi chi invoca, qui decidi cosa può accadere, a prescindere da chi lo invoca.

Tre pezzi: evento, matcher, handler

Un Hook si configura in settings.json (personale, di progetto, o .local.json non condiviso) con tre livelli annidati: l'evento del ciclo di vita a cui si aggancia, il matcher che restringe a quali casi si applica, e l'handler — il comando vero e proprio3.

3. Hooks reference, sezione "Configuration structure".

L'evento decide QUANDO il hook può girare. Il matcher decide SU COSA (qui, solo tool call Bash). L'handler è il comando che gira davvero e decide l'esito con il proprio exit code.

Cosa riceve, cosa restituisce

L'handler riceve JSON su stdin — per un PreToolUse su Bash, include tool_name e tool_input.command. Decide l'esito con l'exit code, non con il testo stampato a caso4:

  • Exit 0: nessuna obiezione. Se stampa JSON su stdout, Claude Code lo interpreta come decisione strutturata (es. permissionDecision); altrimenti flusso normale.
  • Exit 2: errore bloccante. Su PreToolUse, blocca il tool call; su Stop, impedisce a Claude di fermarsi. Il messaggio su stderr torna a Claude come errore.
  • Qualsiasi altro exit code: errore non bloccante — l'esecuzione continua comunque, l'errore finisce solo nel transcript/debug log.

4. Hooks reference, sezione "Exit code semantics". Nota bene: exit 2 su un evento che non può più bloccare nulla (es. PostToolUse, il tool è già girato) non ha lo stesso effetto — dipende dall'evento.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  }
}
#!/bin/bash
COMMAND=$(jq -r '.tool_input.command')
if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Destructive command blocked by hook"
    }
  }'
else
  exit 0
fi

Alla fine di questa lezione saprai: spiegare perché un Hook garantisce ciò che una Skill può solo chiedere, leggere la struttura evento → matcher → handler in settings.json, e distinguere cosa fanno exit 0, exit 2 e ogni altro exit code — inclusa la differenza tra bloccare un PreToolUse e "bloccare" un evento che è già successo.

Mettiti alla prova

1. Qual è la differenza sostanziale tra scrivere "non usare rm -rf" in una Skill e bloccarlo con un Hook?

2. Nell'esempio, il matcher è "Bash" sull'evento PreToolUse. Cosa fa esattamente il matcher?

3. L'handler esce con exit code 2 su un evento PreToolUse. Cosa succede al tool call?

4. Lo stesso exit code 2 su un hook PostToolUse (dopo che il tool è già girato) blocca il tool call allo stesso modo di PreToolUse?

5. Come riceve l'handler le informazioni sul tool call in corso (es. il comando Bash da valutare)?
