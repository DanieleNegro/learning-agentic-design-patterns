Collega un MCP server, e dimostra che funziona

Lezione 0012 — lezione pratica, come la 0008 per le skill e la 0010 per gli hook

Nella 0011 hai visto cosa aggiunge MCP: capacità, cioè tool che l'harness prima non aveva. Qui ne colleghi uno vero e — soprattutto — lo testi. La lezione più importante della 0010 non è arrivata dal quiz ma dal debug: un hook rotto non nega, tace, e il silenzio è indistinguibile dal funzionamento corretto. Con MCP succede la stessa cosa, in tre punti diversi.

Il server è @modelcontextprotocol/server-memory, un server di riferimento del progetto MCP: un knowledge graph persistente (entità, relazioni, osservazioni) salvato in un file JSONL1. È scelto per ragioni didattiche: gira in stdio, non ha auth, ha uno stato che puoi aprire con cat, e ha tool di scrittura e di cancellazione — quindi qualcosa da proteggere.

1. server-memory — modelcontextprotocol/servers. Versione usata e verificata per questa lezione: 2.2.1, 9 tool (create_entities, search_nodes, read_graph, delete_entities…).

Applica subito il criterio della 0011: in questa repo i learning-record fanno già da memoria, quindi qui il server non vince su una Skill. Vincerebbe nel caso che la 0011 chiamava "la ragione forte": lo stesso grafo letto da Claude Code, Claude Desktop e da qualunque altro client MCP, perché il protocollo è aperto.

Alla fine di questa lezione avrai: un MCP server collegato a Claude Code in questa repo, testato a tre livelli diversi, con una persistenza dimostrata fra due sessioni e un Hook che impedisce al modello di cancellare il grafo. Saprai dire cosa dimostra — e cosa non dimostra — ciascuno dei tre test.

Tre livelli di test, tre cose diverse

Ogni livello prova un pezzo della catena e lascia scoperto il resto. Fermarsi al primo è l'errore tipico.

Livello Strumento Cosa dimostra Cosa non dimostra
1. Handshake claude mcp list Il processo parte e risponde al protocollo Che un tool, chiamato, faccia la cosa giusta
2. Protocollo MCP Inspector, tools/call Il server esegue un tool, senza modello di mezzo Che lo faccia con la config che vede Claude Code
3. End-to-end Sessione + tool_result + file Harness, modello e server lavorano insieme Nulla, se guardi il risultato e non la prosa

Passo 1 — collega il server

Dalla root di questa repo:

claude mcp add memory \
  -e MEMORY_FILE_PATH="$PWD/.claude/memory.jsonl" \
  -- npx -y @modelcontextprotocol/server-memory@2.2.1

echo ".claude/memory.jsonl" >> .gitignore

Scope local (il default): il grafo è roba tua, non va condiviso via .mcp.json. Il path è assoluto e lo calcola la tua shell adesso, al momento dell'add: le doppie virgolette fanno espandere $PWD prima che il valore finisca in ~/.claude.json.

Quel dettaglio non è pignoleria: viene da un tentativo fallito, fatto preparando questa lezione. La prima versione usava lo scope project con MEMORY_FILE_PATH=${CLAUDE_PROJECT_DIR:-.}/.claude/memory.jsonl, pensando alla variabile che ha riparato il tuo hook. Risultato reale della chiamata: 

ENOENT: no such file or directory, open
'~/.npm/_npx/eca8d0ea6f1ccf20/node_modules/@modelcontextprotocol/server-memory/dist/.claude/memory.jsonl.lock'

Due difetti in fila, come nella 0010. Primo: CLAUDE_PROJECT_DIR viene iniettata nell'env del server, ma non esiste quando Claude Code espande ${…} nella config — così è scattato il default .. Secondo: il server risolve un path relativo rispetto alla propria cartella, che con npx sta nella cache npm2. Se la cartella fosse esistita, il grafo sarebbe finito lì, e un npm cache clean lo avrebbe cancellato senza alcun errore.

2. Misurato il 2026-11-24 con un claude -p in una cartella di prova e l'output stream-json. La sintassi ${VAR} e ${VAR:-default} in .mcp.json è documentata in MCP — Claude Code Docs; quali variabili esistano in quel momento è un'altra questione.

Passo 2 — livello 1: handshake

claude mcp list | grep memory
# memory: npx -y @modelcontextprotocol/server-memory@2.2.1 - ✔ Connected

✔ Connected vuol dire che il processo è partito e ha completato l'inizializzazione del protocollo. Il server della prova fallita sopra dava esattamente lo stesso segno di spunta: il path sbagliato si scopre solo quando un tool scrive.

Passo 3 — livello 2: protocollo, senza modello

L'MCP Inspector è il client di debug ufficiale. In modalità --cli parla col server come farebbe Claude Code, ma senza nessun LLM a interpretare: chiedi un metodo, ricevi JSON. 

INSPECT="npx -y @modelcontextprotocol/inspector@2.16.0 --cli \
  -e MEMORY_FILE_PATH=$PWD/.claude/memory.jsonl \
  npx -y @modelcontextprotocol/server-memory@2.2.1"

$INSPECT --method tools/list | grep '"name": "'      # i 9 tool esposti

$INSPECT --method tools/call --tool-name create_entities \
  --tool-arg 'entities=[{"name":"Daniele","entityType":"learner","observations":["completed lesson 0011"]}]'

cat .claude/memory.jsonl                              # la verità sta qui

Se l'ultima riga mostra l'entità, il server funziona con quel path. È lo stesso principio del echo '{"tool_input":…}' | script.sh con cui si testava l'hook isolato: togli di mezzo l'harness e interroga il componente da solo.

Passo 4 — livello 3: end-to-end, in due sessioni

Apri una nuova sessione (la config MCP si carica all'avvio) e chiedi: "Salva nel grafo di memoria che ho completato la lezione 0012." Accetta il permesso per il tool. Poi chiudi, apri un'altra sessione e chiedi: "Cosa sai di me dal grafo di memoria?"

La seconda risposta è il test vero: un'informazione sopravvissuta fra due context window che non condividono niente. È la capacità che prima non c'era. Due cose da guardare mentre lo fai:

  • Il tool_result, non la prosa. Nella prova fallita il modello ha risposto con sicurezza citando il tool chiamato, mentre il risultato reale era l'ENOENT di sopra. Espandi la riga della tool call e leggi cosa ha restituito il server; poi cat .claude/memory.jsonl.
  • Il nome del tool. Vedrai mcp__memory__create_entities, preceduto da un ToolSearch: le definizioni dei tool MCP non stanno nel context dall'inizio, vengono caricate quando servono3. È la risposta dell'harness al costo in context che hai visto nella 0011.

3. Osservato nel trace stream-json della prova: ToolSearch con select:mcp__memory__create_entities, poi la chiamata vera. Dettagli in MCP — Claude Code Docs, sezione sul tool search.

Passo 5 — chiudi il cerchio con un Hook

Il tuo hook della 0010 guarda solo il matcher Bash; un tool MCP non passa da lì. Aggiungi in .claude/settings.json un secondo blocco nell'array PreToolUse, accanto a quello esistente: 

{
  "matcher": "mcp__memory__delete_.*",
  "hooks": [
    {
      "type": "command",
      "command": "echo 'Deleting from the memory graph is disabled' >&2; exit 2"
    }
  ]
}

Il matcher è una regex sul nome namespaced, e copre i tre tool delete_entities, delete_observations e delete_relations. Poi il test sul caso positivo, come hai imparato a fare: nuova sessione, "Cancella dal grafo l'entità Daniele". Deve arrivare il messaggio dell'hook, e cat deve mostrare l'entità ancora lì4.

4. Verificato nella prova: l'hook ha bloccato mcp__memory__delete_entities anche con --allowedTools che permetteva esplicitamente quel tool. Una permission rule dice cosa non serve chiedere; un hook con exit 2 su PreToolUse decide cosa non accade.

Mettiti alla prova

1. claude mcp list mostra ✔ Connected. Cosa hai dimostrato?

2. Claude risponde "fatto, ho salvato l'entità nel grafo". Basta come prova?

3. Perché ${CLAUDE_PROJECT_DIR:-.} nel valore di MEMORY_FILE_PATH ha prodotto il default .?

4. Una permission rule consente mcp__memory__delete_entities, un hook su PreToolUse esce con 2 per lo stesso tool. Cosa succede?

5. Ripasso (0003): in un routing, qual è la ragione strutturale per scrivere un handler per categoria invece di un prompt unico?

Quando hai fatto i cinque passi, raccontami cosa hai visto al passo 4 (la risposta della seconda sessione) e al passo 5 (il messaggio dell'hook): così registro l'asse MCP come chiuso con un artefatto reale, come per Skill e Hook. Se qualcosa non torna — un ✔ Connected che poi non scrive, un hook che non scatta — chiedimelo: il debug è la parte che insegna di più. Con questo si chiude l'ultimo asse di estensione; resta l'obiettivo di progettare un workflow multi-step con il Claude Agent SDK.
