Prompt Chaining: il workflow più semplice

Lezione 0002 — il primo dei cinque pattern, e come si scrive letteralmente con pipeline()

Nella lezione 0001 abbiamo fissato l'asse workflow/agent e nominato cinque pattern di workflow in una riga ciascuno. Ora scendiamo nel primo: prompt chaining. È il pattern più semplice perché è l'idea di base da cui discendono tutti gli altri: scomporre un task in una sequenza fissa di chiamate LLM, dove l'output di ogni step diventa l'input del successivo1.

1. Building effective agents — Anthropic Engineering, sezione "Prompt chaining".

Definizione e il ruolo del "gate"

La sequenza da sola non basta a distinguere prompt chaining da un prompt monolitico che fa tutto in un colpo: il punto è che ogni step è più semplice del task intero, e tra uno step e il successivo puoi inserire un gate — un controllo programmatico (non un'altra decisione del modello) che verifica l'output intermedio prima di lasciarlo passare2. Se il gate fallisce, il workflow si ferma o ritenta — in codice fisso, scritto da te.

2. Un gate può essere semplice come una validazione di schema, o sofisticato come un'altra chiamata LLM il cui unico compito è dire "questo output rispetta i criteri?" — resta comunque un predefined code path, perché tu decidi quando e come chiamarlo.

Ogni freccia è codice fisso: nessuno step "decide" se saltare il successivo — lo decide il gate, in modo programmatico.

Quando usarlo

Prompt chaining scambia latenza per accuratezza: più step significano più round-trip, ma ogni singolo step è più facile da far andare bene per il modello, e più facile da testare per te3. Ha senso quando il task si decompone in modo naturale in sotto-task fissi e sequenziali — es. genera un outline, poi verifica che l'outline rispetti dei criteri, poi scrivi il documento completo dall'outline validato.

3. Il trade-off esplicito che Anthropic cita: "trading off latency for higher accuracy by making each LLM call an easier task".

Alla fine di questa lezione saprai: riconoscere uno scenario di prompt chaining e distinguerlo da routing e da un agent loop, spiegare a cosa serve un gate, e scrivere una catena con pipeline() nel Workflow tool.

Mapping sul Workflow tool di Claude Code

Il Workflow tool che hai a disposizione in questa sessione implementa prompt chaining letteralmente con pipeline(): ogni item passa attraverso una sequenza fissa di stage, e lo stage n riceve l'output dello stage n-1. Il gate è semplicemente codice JavaScript ordinario tra due agent(), oppure la validazione automatica che scatta quando passi schema a agent(). 

pipeline(
  items,
  item => agent(`Genera una bozza per ${item}`, { schema: DRAFT_SCHEMA }),
  draft => draft.completa               // <- il gate: un controllo, non un'altra decisione del modello
    ? agent(`Rifinisci: ${draft.testo}`, { schema: DRAFT_SCHEMA })
    : null,                             // fail → stop per questo item
  refined => agent(`Traduci in inglese: ${refined.testo}`)
)

Nota il contrasto con parallel(), che implementa invece il pattern successivo della lista — parallelization — eseguendo più thunk senza dipendenza sequenziale tra loro. La differenza tra i due primitivi nel Workflow tool è la differenza tra prompt chaining e parallelization.

Mettiti alla prova

1. Generi una bozza di changelog dai commit, poi passi la bozza a un secondo step che la riformatta secondo lo stile del progetto, poi un terzo step la traduce in inglese. Che cos'è?

2. Tra il primo e il secondo step della catena inserisci un controllo che verifica che la bozza abbia tutti i campi richiesti prima di lasciarla proseguire. Come si chiama questo controllo nel pattern?

3. Nel Workflow tool, quale primitivo implementa direttamente prompt chaining per un singolo item — cioè fa passare l'output di uno stage come input del successivo?

4. Scomponi "traduci e verifica che non abbia perso termini tecnici" in due step sequenziali invece di un unico prompt che fa entrambe le cose. Cosa guadagni, al costo di più latenza?
